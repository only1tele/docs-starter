---
title: Accept payments from humans and AI agents
subtitle: Create a payment once and let a person or an AI agent complete it through the flow designed for them.
---

One payment obligation, two entry points. You do not have to decide in advance which kind of payer will settle it.

```text
Human payer   ->  checkout URL  ->  a familiar checkout page
AI agent      ->  agent URL     ->  402 Payment Required
```

Both settle the same underlying charge, and both reconcile against the same reference in your own system. This suits invoices, one-off charges, creator and freelancer payments, service fees, subscriptions, recurring billing, prepaid balances, and anything else where the amount is already known and only the payer is uncertain.

A person should not have to understand `402 Payment Required`. An agent should not have to interpret a visual checkout page. Neither is asked to: each gets the entry point built for it, and both settle the same obligation.

<Note title="No MCP required">
This is about giving one payment request a human path and an agent path. You do not need to expose your product through MCP, and the payer does not need a Mitu Agent Wallet.
</Note>

## Universal payments, or agent commerce?

The two look similar and are not. Building on the wrong one is an expensive thing to discover late, so it is worth settling before any code.

**Universal payments starts with the obligation.** You already know what is owed:

```text
"Pay invoice INV-8841 for $125."
```

You create the request, and whoever turns up settles it.

**Agent commerce starts with the journey.** The amount does not exist yet, because nobody has chosen anything:

```text
search -> choose -> price the order -> create it -> pay
```

The agent has to interact with your product before there is anything to pay for.

```text
Universal payments    payment first
Agent commerce        commerce first
```

If the figure is already on an invoice, a quote or a statement, this is the guide. If an agent has to browse your catalogue to arrive at a total, [let AI agents buy from you](/guides/use-cases/agent-commerce) is.

## How it works

```text
Your backend creates one payment link
        |
Mitu returns the payment and its entry points
        |
        +---------------------------+
        |                           |
   Human payer                 AI-agent payer
        |                           |
   checkout URL                agent URL
        |                           |
   the checkout page           402 requirement
        |                           |
   pays by what is           settles by x402
   available to them         or MPP
        |                           |
        +----- payment.completed ---+
                    |
            carrying your reference
                    |
        you reconcile against your own record
                    |
           the money sits in your Mitu balance
                    |
          bank settlement or on-chain withdrawal
```

1. Create a payment link.
2. Get both entry points.

## Before you begin

You need a Mitu merchant account, a server-side API key, an amount somebody owes you, a stable identifier from your own system, and a webhook endpoint for production.

<Warning title="Merchant keys stay on your server">
`sk_live_...` and `sk_test_...` create payment links, invoices and subscriptions. Never put one in a browser, a public checkout page, or an AI client. Nothing the payer touches needs your key.
</Warning>

<Steps toc={true}>

<Step title="Create a payment link">

```bash title="Create a payment link"
curl --request POST \
  --url https://api.mitu.ai/v1/payment-links \
  --header "x-api-key: $MITU_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "type": "charge",
    "amount": 25.00,
    "currency": "USD",
    "description": "Invoice 8841",
    "reference": "ORDER-8841",
    "expiresAt": "2026-10-01T00:00:00Z",
    "paymentMethods": ["x402", "mpp_spt"],
    "metadata": { "order_id": "8841" }
  }'
```

`reference` is the field that makes this manageable later. Set it to something your own system already knows, such as `ORDER-8841`, `INV-2026-441` or `BOOKING-9832`. It comes back on the payment event, so you never have to reconcile against Mitu's id alone.

`metadata` takes free-form values that are returned intact. It is not a place for secrets.

`paymentMethods` constrains what an agent may settle with. Offering more than one costs nothing.

{/* SCREENSHOT: docs/assets/use-cases/universal-payments/create-link.png
     Caption: "Create a payment request once and make it available to human
     and agent payers." */}

[Payment links](/platform/payments/payment-experiences) has every field.

</Step>

<Step title="Use the two entry points">

The create response carries `checkoutUrl`. The agent URL is the same id on the API origin, and the `link.created` event carries both together:

```json title="link.created"
"url": {
  "checkout": "https://mitu.ai/pay/pay_n8d7piu1yc6h",
  "agent": "https://api.mitu.ai/pay/pay_n8d7piu1yc6h"
}
```

Send the **checkout URL** to a person, by email, SMS, WhatsApp, your own app, or on an invoice. Give the **agent URL** to an AI assistant, an agent workflow, or any system that can handle a payment requirement.

<Warning title="They are not interchangeable">
The checkout URL is a page served from the web app. The agent URL answers a payment requirement from the API. Hand an agent the checkout URL and it gets HTML instead of a challenge; open the agent URL in a browser and there is no page to pay on.
</Warning>

{/* SCREENSHOT: docs/assets/use-cases/universal-payments/payment-link-details.png
     Caption: "Each payment request has a checkout path for people and a
     programmatic path for agents." */}

</Step>

<Step title="Let a person pay">

The payer opens the checkout URL and sees who is charging them, what for, how much, and the methods available to them. `link.viewed` fires when the page is opened.

{/* SCREENSHOT: docs/assets/use-cases/universal-payments/human-checkout.png
     Caption: "A person opens the checkout URL and completes the payment."
     Use the real checkout, not a mock-up. */}

</Step>

<Step title="Let an agent pay">

```text
GET  https://api.mitu.ai/pay/pay_abc123   answers 402 with the challenges
POST https://api.mitu.ai/pay/pay_abc123   takes the signed credential
```

<Warning title="402 does not mean the payment failed">
It means payment is required before the request can continue. Nothing has been attempted and nothing has been declined. An integration that logs a 402 as a failed payment will show a failure for every successful agent payment you take.
</Warning>

It tells the agent how much is due, in what, which methods you accept, and what it needs to settle one.

```text
Agent requests the agent URL
        |
402 with the payment requirement
        |
It picks a method it supports
        |
It settles
        |
It submits the credential
        |
Payment completes
```

Agents pay through x402 and MPP, depending on what you accepted on the link and what the payer can satisfy. `mpp_spt` is the card-backed method within MPP rather than a third protocol beside them.

{/* SCREENSHOT: docs/assets/use-cases/universal-payments/agent-payment.png
     Caption: "An agent receives a machine-readable payment requirement and
     pays programmatically." */}

[The 402 payment flow](/platform/payments/agent-payments) covers each field and [payment methods](/platform/payments/agent-payments) each method.

</Step>

<Step title="Track viewed and paid">

```text
link.created      you made the link
link.viewed       somebody opened the checkout page
payment.completed it was paid
```

Both link events carry the payment link id and your `reference`. `link.viewed` comes from somebody opening the checkout page, so do not treat it as a general "somebody is interested" signal covering the agent path.

{/* SCREENSHOT: docs/assets/use-cases/universal-payments/payment-activity.png
     Caption: "Track when a payment request is opened and when payment
     completes." */}

</Step>

<Step title="One payment, one reconciliation">

This is the part that makes the product click. Both paths end in the same place.

```text
Human route                      Agent route

INV-8841                         INV-8841
    |                                |
checkout page                    agent URL, 402
    |                                |
pays by card or wallet           settles by x402 or MPP
    |                                |
    +--------- payment.completed ----+
                    |
            reference: INV-8841
                    |
        one handler, one database row
```

Your backend does not branch on who paid. It reads `reference`, finds `INV-8841`, and marks it paid. The two payer experiences exist so that neither payer has to pretend to be the other; they do not have to become two integrations on your side.

Do not make Mitu's ids the only identifiers your application understands, and do not mark anything paid from the payer's browser or from what an AI client reported. Use the verified webhook, or read the state back from the API.

</Step>

<Step title="List, read and update links">

```text
GET    /v1/payment-links       list them
GET    /v1/payment-links/{id}  read one
PATCH  /v1/payment-links/{id}  amend one
DELETE /v1/payment-links/{id}/cancel
```

The list filters on `type`, `status`, `reference` and `source`. Filtering by your own `reference` is the useful one: it answers "is there already a link for this invoice" without you having stored Mitu's id.

A `PATCH` changes `expiresAt`, `description`, `reference` and `metadata`. It does not change the amount or the currency. To charge a different figure, cancel the link and create another, so that a link somebody is already looking at cannot change price under them.

</Step>

<Step title="Use invoices for formal billing">

Where the payment belongs to an accounts-receivable workflow, an invoice carries line items, tax, a discount, a due date and an invoice number, and it moves through a lifecycle rather than simply being paid.

```text
Create a draft
        |
Send it
        |
The customer receives a payment request
        |
A person or an agent pays it
        |
The invoice is marked paid
```

Creating and sending are separate calls, so a draft can be amended before the customer sees it. A sent invoice is payable through the same two entry points, on the `/invoice/` segment.

{/* SCREENSHOT: docs/assets/use-cases/universal-payments/invoice.png
     Caption: "Use invoices where the payment belongs to a formal billing
     workflow." */}

[Invoices](/platform/payments/invoices) covers the schema and the lifecycle.

</Step>

<Step title="Use subscriptions for recurring payments">

A plan defines what recurs and how often. A subscription attaches a payer to one.

```text
Create a plan
        |
Create a subscription against it
        |
The charge falls due
        |
It is collected
        |
The subscription state updates
```

<Warning title="Recurring charges settle over MPP only">
`x402` is a one-time authorisation signed for a specific amount and recipient, so it cannot carry a future charge. A subscription takes `mpp_crypto` or `mpp_spt`.
</Warning>

{/* SCREENSHOT: docs/assets/use-cases/universal-payments/subscription.png
     Caption: "Use subscriptions when the payer keeps a recurring service
     active." */}

[Subscriptions](/platform/payments/subscriptions) covers plans, states and the invoices a subscription generates.

</Step>

<Step title="Use sessions for prepaid usage">

A payment link of type `session` has the payer fund a balance up front and draw it down across many calls, rather than settling each one.

```text
The payer funds the session
        |
session.opened, with the deposit and the on-chain channel
        |
Calls draw against the balance
        |
session.closed, with what was spent and what was refunded
```

Use it where a payment per call would dominate the exchange. [Payment links](/platform/payments/payment-experiences) covers the `sessionMaxDeposit` and `sessionExpiresAt` fields.

</Step>

<Step title="Receive events through webhooks">

Production payment state comes from webhooks, not from the browser, the AI client or the dashboard.

```text
Receive the delivery
        |
Verify the signature with this endpoint's whsec_ secret
        |
Check event_id
        |
Already processed? Acknowledge and stop
        |
Apply the state change
        |
Answer 2xx
```

<Warning title="Two secrets, two directions">
`whsec_...` signs webhook deliveries Mitu sends to you, and is the one that matters here. `mps_...` signs paid requests Mitu forwards to your API on an agent's behalf. They are different secrets for opposite directions.
</Warning>

Every retry carries the same `event_id`, so deduplicating on it is what stops one payment being applied twice.

{/* SCREENSHOT: docs/assets/use-cases/universal-payments/webhook.png
     Caption: "Subscribe to payment events and use webhooks as the source of
     truth for backend payment state." Mask the secret. */}

[Webhooks](/platform/webhooks/overview) covers delivery and retries.

</Step>

<Step title="Handle failed payments">

`payment.failed` fires when a payment was attempted and did not complete, carrying the amount, the method, your `reference` and a `reason`:

```text
no_supported_method    the payer could satisfy none of the methods you accept
insufficient_balance   they did not have the funds
over_limit             a wallet limit stopped it
settlement_failed      the settlement itself did not go through
upstream_rejected      the payment was refused upstream
```

Not every reason is retryable, and they call for different responses. `no_supported_method` usually means the methods on the link are too narrow for the payers you are reaching.

</Step>

<Step title="Settle the funds">

Everything you receive lands in your Mitu balance as USDC, whoever paid and however. From there you either settle in local currency to your bank account, or withdraw the stablecoin on-chain to an address you control.

How somebody paid you has no bearing on how you take the money out. [Payouts](/platform/payments/settlement) covers both.

{/* SCREENSHOT: docs/assets/use-cases/universal-payments/balance-settlement.png
     Caption: "Settle received funds to your bank account or withdraw
     stablecoin on-chain." */}

</Step>

</Steps>

## End to end: one invoice, either payer

<Steps>

<Step title="You create the request">
One call, and you are done with the decision about who pays.

```json
{
  "type": "charge",
  "amount": 125.00,
  "currency": "USD",
  "description": "Design services",
  "reference": "INV-8841",
  "paymentMethods": ["x402", "mpp_spt"]
}
```
</Step>

<Step title="Mitu returns both paths">
`checkoutUrl` comes back on the response. Both URLs arrive together on `link.created`.

```json
{
  "checkout": "https://mitu.ai/pay/pay_n8d7piu1yc6h",
  "agent": "https://api.mitu.ai/pay/pay_n8d7piu1yc6h"
}
```
</Step>

<Step title="Whoever shows up pays">
Neither payer has to pretend to be the other.

```text
A person   opens the checkout and pays with what is available to them
An agent   GETs the agent URL, reads the 402, settles by x402 or mpp_spt
```
</Step>

<Step title="You are told once">
The same event either way, carrying your own reference.

```json
{
  "event": "payment.completed",
  "event_data": {
    "source": "link",
    "payment_link_id": "pay_n8d7piu1yc6h",
    "amount_paid": "125.00",
    "reference": "INV-8841"
  }
}
```
</Step>

<Step title="You reconcile">
One handler, one row, no branch on who paid.

```text
reference: INV-8841  ->  find INV-8841  ->  mark it paid
```
</Step>

<Step title="You settle">
The money sits in your Mitu balance as USDC until you send it to your bank or withdraw it on-chain.
</Step>

</Steps>

One obligation, two payer experiences, one reconciliation path.

## Common mistakes

<AccordionGroup>

<Accordion title="Treating the agent URL like a checkout page">
It is a programmatic payment endpoint, not a page. Opening it in a browser shows no checkout, and sending an agent the checkout URL hands it HTML where it expected a challenge. They are different hosts serving different things, and the `link.created` event gives you both so you never have to guess which is which.
</Accordion>

<Accordion title="Treating 402 as a failed payment">
It is the payment requirement, not a decline. Nothing has been attempted at that point. Logging it as a failure means every successful agent payment you take appears in your metrics as a failure first.
</Accordion>

<Accordion title="Putting a merchant key in client code">
`sk_live_...` and `sk_test_...` create payment links, invoices and subscriptions. Nothing the payer touches needs one. The checkout page needs no key at all, and the agent URL needs the payer's credential, not yours.
</Accordion>

<Accordion title="Marking an order paid from the browser">
A redirect back to your site says the payer reached the end of a page, not that money moved. Use `payment.completed`, verified against the webhook secret, or read the state back from the API. This matters more on the agent path, where there is no browser to return from.
</Accordion>

<Accordion title="Ignoring `reference`">
Without it, every reconciliation has to start from a Mitu id you had to store and keep in step with your own record. With it, the payment event names your own invoice and the handler is two lines. It costs nothing to set at create time and is awkward to retrofit.
</Accordion>

<Accordion title="Confusing whsec_ with mps_">
`whsec_...` signs webhook deliveries Mitu sends you. `mps_...` signs paid requests Mitu forwards to your API on an agent's behalf. They sign opposite directions and are not interchangeable. Verifying a webhook with the wrong secret fails every delivery, which usually gets diagnosed as a delivery problem rather than a key problem.
</Accordion>

<Accordion title="Waiting for settlement.completed">
It is a declared event type that nothing currently emits. A flow that waits for it waits forever. Reconcile against `payment.completed`, which fires for every payment you receive.
</Accordion>

</AccordionGroup>

## The result

You can accept a payment without knowing in advance whether a person or an agent will settle it.

**You control** the amount, the description, the reference, the link type, the methods you accept, the invoice and subscription lifecycles, and where the money goes. **Mitu provides** the checkout, the agent entry point, the payment requirement, the payment state, invoices, subscriptions, sessions, webhooks, and the balance you settle from.
