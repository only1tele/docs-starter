---
title: Let AI agents buy from you
subtitle: Let agents discover what you sell, check current prices and availability, place an order or booking, pay for it, and receive a confirmation from the system you already run.
---

Your commerce API stays responsible for products, inventory, availability, pricing, taxes, fees, orders, reservations, fulfilment and cancellations. Mitu makes the operations you choose available as MCP tools, and handles the payment requirement before a paid request reaches you.

You do not rebuild your store, booking system or order engine for agents. The endpoints that already serve your website and app become capabilities an agent can use, because an agent is another client of the same API.

```text
Website ------+
Mobile app ---+---> Your existing commerce API
AI agent -Mitu+
```

A restaurant might expose:

```text
get_menu              GET   /menu      free
check_delivery_zone   GET   /zones     free
create_order          POST  /orders    dynamic
get_order             GET   /orders/{id}
```

And a customer asks their agent:

```text
Order two chicken wraps and a bottle of water and deliver them to my saved address.
```

The agent reads the menu, confirms the address is serviceable, requests the order, settles the charge, and hands back the confirmation your API produced.

<Note title="Your system stays the source of truth">
Mitu provides the agent-facing commerce and payment layer around your API. Prices, stock, availability, totals, order state and fulfilment remain yours. An agent should never be the authority on what something costs.
</Note>

<Note title="Every endpoint here is yours, not Mitu's">
`/menu`, `/orders`, `/bookings` and the rest are examples of your own API. They are not Mitu routes, and Mitu prescribes no order schema. The only Mitu surface in this guide is the configuration you do in the dashboard and the headers that arrive on a forwarded request.
</Note>

## What you will build

1. Connect your existing commerce API to Mitu.
2. Register the operations an agent needs to complete a transaction.
3. Separate discovery from the transaction itself.
4. Decide which operations need a signed-in customer.
5. Price the transaction endpoint.
6. Connect the MCP from an agent client.
7. Let the agent discover what the customer can buy.
8. Let it create the order, booking or reservation.
9. Return a payment requirement for the total.
10. Let the agent pay.
11. Receive the paid request.
12. Verify and deduplicate it, then create the transaction.
13. Return the confirmation.
14. Track payment and delivery.
15. Handle the case where payment succeeded and delivery did not.

## Before you begin

You need:

- A Mitu merchant account.
- An existing HTTP API for what you sell.
- Operations covering the steps an agent needs to finish a transaction.
- Your Mitu signing secret configured in your backend.
- A way for your backend to calculate the final amount.
- Customer authentication, if the transaction needs an existing account.

Your API probably already has something like one of these. Mitu works with the design you have, so none of these routes are required:

```text
Retail      GET /products    GET /products/{id}   POST /orders     GET /orders/{id}
Booking     GET /availability                     POST /bookings   GET /bookings/{id}
Restaurant  GET /menu        GET /zones           POST /orders     GET /orders/{id}
```

<Steps toc={true}>

<Step title="Connect your commerce API">

In the dashboard, set the base URL of the API that already powers your commerce experience.

```text
https://api.example.com
```

If your website or app already calls it to browse inventory, price a basket, create an order or book a slot, those are the operations you can offer to agents.

Mitu holds no credential for your API. Every forwarded request is signed with a secret Mitu issues you, and your backend verifies it.

{/* SCREENSHOT: docs/assets/use-cases/agent-commerce/integration-api.png
     Caption: "Connect the API that already powers your products, orders,
     bookings or services." Show the base URL, the health-check path and the
     customer sign-in setting. No secrets visible. */}

[The MCP](/platform/mcp/overview) covers the layer in front, and [request signature verification](/platform/security/request-verification) covers what arrives at your endpoint.

</Step>

<Step title="Register the commerce operations">

Register the operations an agent needs to finish the journey. Do not register every internal operation merely because it exists: a tool list full of things an agent should never call makes it more likely to call one.

```text
Retail        search_products      get_product        create_order        get_order
Restaurant    get_menu             check_delivery_zone create_order       get_order
Hotel         search_availability  get_room           create_booking      get_booking
Appointments  list_services        check_availability create_appointment  get_appointment
```

Each record tells the agent what the operation does, when to reach for it, what it accepts, what it returns, whether the caller must be signed in, and whether it is paid.

```yaml
name: create_order
method: POST
path: /orders
description: Creates an order from the selected items and delivery details
when_to_use: Use after the customer has confirmed the items, quantities and delivery details
pricing_type: dynamic
requires_auth: true
```

That is a description of the endpoint record, not a request body. Endpoints are configured in the dashboard.

`when_to_use` carries more weight in commerce than anywhere else, because the cost of a wrong tool choice is an order the customer did not ask for. Say what must already be confirmed before the call makes sense.

If you maintain an OpenAPI document, import it rather than recreating each operation by hand.

{/* SCREENSHOT: docs/assets/use-cases/agent-commerce/endpoints.png
     Caption: "Register the operations an agent needs to complete the
     transaction." Use a populated list. */}

[MCP endpoints](/platform/mcp/endpoints) has the full field reference and guidance on designing a set of tools.

</Step>

<Step title="Separate discovery from the transaction">

A commerce integration usually has free discovery operations and a paid transaction operation:

```text
get_menu              free
check_delivery_zone   free
create_order          dynamic
```

The agent needs enough information to make a correct decision before it commits money. Free discovery is the usual way to give it that, though it is your call: nothing forces a merchant to make discovery free.

What is not optional is where the information comes from. Your API stays authoritative for current price, availability, stock, tax, delivery fee, service fee, discounts and the final total. Do not put volatile commercial information in a tool description, where it will be read once at connection time and then go stale.

A third group is worth registering too: a status operation such as `get_order` or `get_booking`, so an agent can answer "where is my order" without placing another one.

</Step>

<Step title="Decide whether the customer must sign in">

Some purchases complete without an account. Others need the agent to act for somebody you already know.

| Needs an identified customer | Can often be anonymous |
| --- | --- |
| Saved addresses and payment preferences | A public catalogue or menu |
| Account-specific prices and loyalty benefits | Published availability |
| Order or booking history | Delivery-zone checks |
| Booking against an existing profile | Generally available stock |

These are your decisions, not platform rules. Set `requires_auth` per endpoint, so a public menu stays open while `create_order` requires a signed-in customer.

Two methods are available. Use **OAuth** when customers should sign in with the account they already have with you, in which case Mitu forwards their access token and your existing account rules keep applying. Use a **customer key** when you would rather provision the customer yourself and hand them an `mcpk_...` credential.

[MCP authentication](/platform/mcp/authentication) covers both, and [Bring your product to AI agents](/guides/use-cases/agent-channels) walks through setting either up from scratch.

</Step>

<Step title="Price the transaction endpoint">

Commerce usually needs dynamic pricing, because the amount depends on the transaction:

```text
Items       $42.00
Delivery     $5.00
Tax          $3.76
-----------------
Total       $50.76
```

The agent must not work that out. Your backend calculates it with the same rules it uses for every other channel.

Dynamic pricing calls your endpoint twice, and one header tells the calls apart:

```text
No x-mitu-amount-charged   A quote. Validate, calculate, return 402 with the price.
                           Do not create the order.

Header present             Payment has settled. Verify, then create the order.
```

<Warning title="Do not create the order during the quote">
The quote leg runs on every call, before any money moves. Creating or fulfilling the transaction there produces orders nobody paid for, and a duplicate when the paid leg arrives.
</Warning>

If what you sell genuinely costs the same every time, use fixed pricing instead. Do not reach for dynamic pricing when there is nothing to calculate.

{/* SCREENSHOT: docs/assets/use-cases/agent-commerce/dynamic-pricing.png
     Caption: "Configure the transaction endpoint to use the pricing model
     that matches your checkout logic." */}

[Dynamic pricing](/platform/payments/pricing) covers both legs, and [endpoint types](/platform/payments/pricing) the other models.

</Step>

<Step title="Connect the MCP from an agent client">

```text
https://mcp.mitu.ai/mcp
https://mcp.example.com/mcp
```

Connections use Streamable HTTP. If your flow needs an existing account, connect with the customer key or OAuth method you configured.

Once connected, the agent sees your commerce tools:

```text
get_menu
check_delivery_zone
create_order
get_order
```

{/* SCREENSHOT: docs/assets/use-cases/agent-commerce/claude-tools.png
     Caption: "The merchant's commerce capabilities are available to the
     customer's agent." Use a real populated tool list. */}

[Domain and integration](/platform/mcp/domains) covers moving to your own URL.

</Step>

<Step title="Let the agent discover what the customer can buy">

```text
Customer asks for two chicken wraps and water
        |
Agent calls get_menu
        |
Agent calls check_delivery_zone
        |
Agent calls create_order
```

The agent reads the current menu and delivery rules from your API rather than from whatever the model remembers about your business. The same shape holds elsewhere: `search_availability` then `get_room` then `create_booking`, or `search_products` then `get_product` then `create_order`.

{/* SCREENSHOT: docs/assets/use-cases/agent-commerce/claude-discovery.png
     Caption: "The agent uses your discovery tools to understand the current
     options before creating the transaction." */}

</Step>

<Step title="Create the order, booking or reservation">

With the details confirmed, the agent calls the transaction tool.

```json title="Illustrative arguments for your own create_order"
{
  "items": [
    { "product_id": "wrap_chicken", "quantity": 2 },
    { "product_id": "water_500ml", "quantity": 1 }
  ],
  "delivery_address_id": "addr_456"
}
```

That schema is yours. Use whatever your API already accepts.

Validate it as you would any other client: product identifiers, quantities, availability, service area, customer eligibility, current pricing, taxes and fees, and every other rule you already enforce. An agent is not a trusted caller merely because it reached you through Mitu.

On a dynamic endpoint, this first call is the quote.

</Step>

<Step title="Return the payment requirement">

Your 402 becomes the payment requirement the agent sees.

```text
Order request
        |
You calculate the authoritative total
        |
402 with the amount
        |
Mitu returns a payment requirement listing what you accept
        |
Agent picks a method it can settle
```

The requirement names the service, the endpoint, the amount, and every method you accept. It is not an error: it is the protocol saying what must happen for the call to continue. [The 402 payment flow](/platform/payments/agent-payments) covers each field.

</Step>

<Step title="The agent pays">

The agent settles one of the challenges. **x402** settles USDC on Base, **`mpp_crypto`** settles USDC on Tempo, and **`mpp_spt`** is a card-backed payment for payers with no wallet. You choose which to accept; the agent picks what it can satisfy. See [payment methods](/platform/payments/agent-payments).

If the caller is one of your own customers and holds a wallet you issued, their agent can settle from it by name:

```text
pay({ endpoint: "/orders", method: "POST", body: {...}, wallet: "Travel" })
```

The destination is always your own endpoint. An agent cannot redirect that payment elsewhere.

<Note title="Wallets stay optional">
An external agent can buy from you without any Mitu wallet existing. [Agent Wallets](/platform/agent-wallets/overview) are for merchants who want to give their own customers spending power, and they are not a prerequisite for selling.
</Note>

{/* SCREENSHOT: docs/assets/use-cases/agent-commerce/claude-payment.png
     Caption: "The agent satisfies the transaction's payment requirement
     before the order or booking is completed." */}

</Step>

<Step title="Receive the paid request">

Settlement is confirmed before your endpoint is called again. The paid call carries the amount:

```http
x-mitu-amount-charged: 50.760000
x-mitu-request-id: req_...
x-mitu-signature: t=...,v1=...
x-mitu-agent-id: ...
```

When the payer is a customer you know, it also carries `x-mitu-customer-id` and `x-mitu-customer-ref`. Under OAuth it carries their `authorization` token. An agent buying from you anonymously has none of these, and that is normal rather than a fault.

</Step>

<Step title="Verify, deduplicate, then create the transaction">

```text
Paid request received
        |
Verify x-mitu-signature against the raw body
        |
Check the timestamp
        |
Look up x-mitu-request-id
        |
Already processed? Return the existing order. Stop.
        |
Validate the commerce request again
        |
Create the order or booking
        |
Store req_id -> order_id, and return the confirmation
```

Verify before you trust anything in the request. The customer id is a plain header and means nothing until the signature proves the call came from Mitu.

<Warning title="Deduplicate, or sell the same thing twice">
A delivery can be retried, and a commerce endpoint has side effects. Without a check on `x-mitu-request-id`, a retry creates a second order or a second reservation for one payment. This is the single most consequential mistake in a commerce integration.
</Warning>

Treat `x-mitu-request-id` as the idempotency key for anything Mitu delivers, and persist the mapping:

```text
req_abc123 -> order_8841
```

A retry for `req_abc123` must resolve to `order_8841`, not create `order_8842`. [Request signature verification](/platform/security/request-verification) has the algorithm, a worked implementation and the idempotency pattern in full.

</Step>

<Step title="Return the confirmation">

Return the response your API already returns.

```json title="Your own order response"
{
  "id": "order_8841",
  "status": "confirmed",
  "total": 50.76,
  "currency": "USD",
  "estimated_delivery": "35-45 minutes"
}
```

```json title="Or a booking"
{
  "id": "booking_2107",
  "status": "confirmed",
  "check_in": "2026-10-18",
  "check_out": "2026-10-20",
  "total": 420,
  "currency": "USD"
}
```

Mitu passes it back to the agent, which tells the customer what happened. Return a stable identifier and a clear status, because they are what the agent repeats back and what a later `get_order` call will be made with.

{/* SCREENSHOT: docs/assets/use-cases/agent-commerce/claude-confirmation.png
     Caption: "The agent receives the confirmed transaction from your existing
     commerce API." */}

</Step>

<Step title="Track payment and delivery">

Two questions, and they have separate answers: was the payment completed, and was your request delivered successfully?

`payment.completed` fires when you are paid and carries `delivered`. If the payer used a wallet you issued, `wallet.debited` describes the same movement from their side, joined to yours by `tx_hash`. It does not fire for every commerce payment, only for wallet ones.

{/* SCREENSHOT: docs/assets/use-cases/agent-commerce/payment-details.png
     Caption: "Track the payment and delivery state for the completed
     transaction." */}

Do not make the dashboard your only source of payment state in production. [Webhooks](/platform/webhooks/overview) covers delivery and retries, and [events](/platform/webhooks/events) has the payloads.

</Step>

<Step title="Handle paid but not delivered">

Settlement happens before your endpoint is called, so a failure afterwards leaves you paid and the customer with nothing. In commerce that is not an accounting note, it is an undelivered order.

```text
payment succeeds -> your order service returns 500
payment succeeds -> inventory rejects the order
payment succeeds -> a booking dependency is unavailable
```

```json title="payment.completed"
{
  "delivered": false,
  "failure_status": 500
}
```

An on-chain settlement is final and no retry returns the money. Treat it as a fulfilment problem: create the order by hand, complete the booking out of band, contact the customer, or refund them. `x-mitu-customer-ref` on the original request maps to your own record, which is usually how you reach them.

{/* SCREENSHOT: docs/assets/use-cases/agent-commerce/paid-not-delivered.png
     Caption: "Monitor transactions where payment succeeded but the commerce
     request was not delivered." */}

[Paid but not delivered](/platform/payments/agent-payments) covers the state and the causes worth ruling out.

</Step>

</Steps>

## End to end: a restaurant order

<Steps>

<Step title="The customer asks">
"Order two chicken wraps and a bottle of water and deliver them to my saved address."
</Step>

<Step title="The agent reads the menu and checks delivery">
Two free discovery calls, so it is working from your current data rather than from what the model remembers.

```text
get_menu             -> current items and their identifiers
check_delivery_zone  -> the saved address is serviceable
```
</Step>

<Step title="It requests the order">
Because the endpoint is dynamic, this first call arrives with no `x-mitu-amount-charged`, which makes it a quote.

```json
{
  "items": [
    { "product_id": "wrap_chicken", "quantity": 2 },
    { "product_id": "water_500ml", "quantity": 1 }
  ],
  "delivery_address_id": "addr_456"
}
```
</Step>

<Step title="You price it">
Items \$42.00, delivery \$5.00, tax \$3.76. Answer 402 with the total and create nothing.

```json
{ "amount": "50.76", "currency": "USD" }
```
</Step>

<Step title="The agent pays">
It picks a method you accept and settles it. If it is your own wallet customer, it may settle from a wallet it is allowed to use.
</Step>

<Step title="Mitu delivers the paid request">
The same body arrives again, now carrying the amount.

```http
POST /orders
x-mitu-signature: t=1757601312,v1=6b21de...
x-mitu-request-id: req_5f13b916
x-mitu-amount-charged: 50.760000
```
</Step>

<Step title="You verify and create">
Check the signature against the raw body, check the timestamp, look up the request id, and validate stock once more. Then create the order and store the mapping in the same transaction.

```text
req_5f13b916 -> order_8841
```
</Step>

<Step title="The agent confirms">
It returns your own response to the customer.

```json
{
  "id": "order_8841",
  "status": "confirmed",
  "total": 50.76,
  "currency": "USD",
  "estimated_delivery": "35-45 minutes"
}
```
</Step>

</Steps>

## The result

Your commerce system now serves agents as another transaction channel. You keep the catalogue, inventory, availability, pricing, taxes, customer rules, order creation, fulfilment, cancellations and refunds. Mitu provides discovery, the agent-facing tools, customer authentication where you need it, payment requirements, the payment methods, signed delivery, and the events that tell you what happened.
