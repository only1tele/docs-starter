---
title: Issue wallets to customers
subtitle: Give your customers Agent Wallets their AI agents can spend from, with spending limits and approval controls you configure.
---

An Agent Wallet belongs to your customer. You create and operate it, they fund it, and their agent can spend the balance through Mitu's wallet tools. The agent cannot create wallets, withdraw, or change the controls.

```text
You          create and operate the wallet
Your customer owns the funds
Their agent   spends through controlled tools
Mitu          holds the wallet and enforces the controls
```

<Note title="A wallet exists only because you created one">
Signing in does not create one. Reading a balance does not create one. Connecting an AI client does not create one. A customer with no wallet has no balance and no address, and that is a real state rather than a missing one.

This is deliberate: a wallet costs real addresses to fund and splits a customer's money into a pot, so it is your decision rather than something an agent can bring about.
</Note>

## What you will build

1. A Mitu customer mapped to the customer in your own system.
2. A wallet issued to them, named for its purpose.
3. Spending controls on it.
4. Funding instructions, and a funded wallet.
5. The customer connected by key or OAuth.
6. Their agent able to read and spend from the wallet.
7. Credits and debits visible to you.

## Before you begin

You need a Mitu merchant account, a server-side merchant key, a backend that can call the API, and a customer, unless your customers arrive through OAuth.

<Warning title="Two keys, and only one ever leaves your server">
`sk_live_...` and `sk_test_...` create customers and wallets. They belong on your server. `mcpk_...` is what a customer receives: it identifies them to your MCP, holds no funds, and cannot create a wallet or read your account.
</Warning>

<Steps toc={true}>

<Step title="Create the customer">

Every wallet belongs to a customer.

```bash title="Request"
curl --request POST \
  --url https://api.mitu.ai/v1/customers \
  --header "x-api-key: $MITU_API_KEY" \
  --header "Idempotency-Key: customer-your_user_8841" \
  --header "Content-Type: application/json" \
  --data '{
    "client_reference_id": "your_user_8841",
    "first_name": "Ada",
    "last_name": "Obi",
    "email": "ada@example.com",
    "phone": "+2348099887766"
  }'
```

```json title="201 Created"
{
  "id": "cus_ds9hazr8jd3l",
  "client_reference_id": "your_user_8841",
  "first_name": "Ada",
  "last_name": "Obi",
  "email": "ada@example.com",
  "phone": "+2348099887766",
  "key": "mcpk_3a6f9d2a6bbc816b11d524fe052b26b7e75fb7b5fa7a1a7d",
  "mcp_url": "https://mcp.yourdomain.com/mcp",
  "created_at": "2026-09-11T15:00:34.915Z"
}
```

<ParamField path="client_reference_id" type="string">
  Your own identifier for the person. It keeps the Mitu customer tied to the record you already have, comes back on every event as `customer_ref`, and is what makes this call safe to retry.
</ParamField>

<ParamField path="key" type="string">
  The customer's MCP key, returned once. Only a hash is stored, so it cannot be shown again. Capture it here if the customer will connect by key.
</ParamField>

<ParamField path="mcp_url" type="string">
  Where their AI client connects.
</ParamField>

**Idempotency.** Send an `Idempotency-Key`. The same key within 24 hours returns the original response byte for byte. The same key with a *different* body returns `409`, which means something changed between attempts rather than that a retry failed.

**Already have the customer?** Reuse them. Do not create a second because the same person has started using an agent. If they arrived through your OAuth, Mitu created them on first sign-in from their `sub`, and `customer.created` told you the id.

**Observable result:** the customer appears under `GET /v1/customers`, and holds no wallet yet.

</Step>

<Step title="Issue the wallet">

```bash title="Request"
curl --request POST \
  --url https://api.mitu.ai/v1/customers/cus_ds9hazr8jd3l/wallets \
  --header "x-api-key: $MITU_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "name": "Travel",
    "limits": { "per_payment": 250, "monthly": 2000, "approve_above": 150 }
  }'
```

```json title="201 Created"
{
  "id": "wal_fc2ff966abc04de09c22",
  "customer_id": "cus_ds9hazr8jd3l",
  "name": "Travel",
  "currency": "USDC",
  "limits": {
    "per_payment": 250,
    "monthly": 2000,
    "approve_above": 150,
    "currency": "USD"
  },
  "addresses": [
    { "network": "base",   "address": "0xd7Ca1fdA..." },
    { "network": "tempo",  "address": "0xd7Ca1fdA..." },
    { "network": "solana", "address": "3c6SpTNK..." }
  ],
  "created_at": "2026-09-11T15:01:32.760Z"
}
```

<ParamField path="id" type="string">
  `wal_...`, the wallet's identifier.
</ParamField>

<ParamField path="currency" type="string">
  The wallet holds `USDC`. The limits on it are USD, which is why the limits object names its own currency.
</ParamField>

<ParamField path="addresses" type="array">
  One entry per supported network. **Only the create response carries these.** `GET /v1/customers/{id}/wallets` returns names and limits without addresses, so capture them here or read them from the wallet's own address route when you need them again.
</ParamField>

Creating the same name twice returns the wallet that already exists, so the call is safe to retry.

{/* SCREENSHOT: docs/assets/integration-guides/issue-wallets/create-wallet.png
     Caption: "Issue an Agent Wallet and configure how the customer's agent
     can spend from it." Show the customer, the name and the controls. */}

**Observable result:** `wallet.created` fires with the wallet's id, name, limits and addresses.

</Step>

<Step title="Name it for how the customer will use it">

The name is not a label for your records. It is the word the customer says and the word their agent passes.

```text
"Book the flight from Travel."
```

| Good | Poor |
| --- | --- |
| `Travel` | `Wallet 1` |
| `Office` | `Wallet 2` |
| `Research` | `Other` |
| `Groceries` | `Account B` |

Names are unique per customer and are effectively permanent once somebody starts saying one. [Multiple wallets](/platform/agent-wallets/multiple-wallets) covers designing a set.

</Step>

<Step title="Configure the spending controls">

All three are USD while the balance is USDC.

<ParamField path="monthly" type="number">
  The most this wallet may spend in a calendar month.
</ParamField>

<ParamField path="per_payment" type="number">
  The intended ceiling for a single payment.
</ParamField>

<ParamField path="approve_above" type="number">
  The intended threshold above which a payment waits for the customer.
</ParamField>

<Warning title="Only the monthly limit currently gates a payment">
`monthly` is the control that changes what happens today: a payment that would take the wallet past it is held for the customer to approve rather than settling. `per_payment` and `approve_above` are accepted, stored and returned on the wallet and on `wallet.created`, but nothing in the payment path reads them yet.

Do not present either to your customers as an enforced control until that changes.
</Warning>

**How they are meant to interact.** With a \$1,000 balance and the limits above, a \$80 payment is routine, a \$200 payment crosses `approve_above` and waits for the customer, and a \$400 payment exceeds `per_payment` and is refused. Today only the monthly ceiling produces the hold.

**Inherited limits.** A limit you omit is inherited from the limits that customer already has. Omitted does not mean unlimited, and zero means no limit rather than a ceiling of zero. If you want a wallet bounded, set the field.

**Changing them later.** There is no public endpoint for updating a wallet's limits. They are set at creation and changed from the dashboard.

{/* SCREENSHOT: docs/assets/integration-guides/issue-wallets/spending-controls.png
     Caption: "Set what the agent can spend and when the customer is asked." */}

</Step>

<Step title="Fund the wallet">

The customer funds it. The balance is theirs, not yours.

Send USDC to the wallet's address on a network it supports. Deposits are detected on chain and credited automatically.

```text
base:   0xd7Ca1fdA...      Base and Tempo share one EVM address
tempo:  0xd7Ca1fdA...
solana: 3c6SpTNK...        a different address entirely
```

<Warning title="Show the address with its network">
An EVM address cannot receive on Solana, and funds sent to the wrong chain are not recoverable. Present the pair, never a single bare address. The create response tells you which serves which.
</Warning>

Each wallet has its own addresses, so funding Travel never touches Office.

Wallets can also be funded by local bank transfer in NGN, USD, EUR, GBP, MXN, BRL and COP.

<Step title="Confirm it was credited">

`wallet.credited` fires when a deposit lands.

```json title="wallet.credited"
{
  "event": "wallet.credited",
  "event_id": "evt_u0b5zq2xlk8mpn1k",
  "event_created_at": "2026-09-09T18:41:50.204Z",
  "event_data": {
    "customer_id": "cus_0t9549fps3xd",
    "customer_ref": "auth0|68f3c2a1b9",
    "wallet_id": "wal_65286515b43d4e3eba93",
    "amount": "0.067000",
    "currency": "USDC",
    "network": "base",
    "address": "0xCD2CEd9732...",
    "tx_hash": "0x7c1e4a902f6b...",
    "balance_after": "0.067000"
  }
}
```

`balance_after` is that wallet alone, not everything the customer holds. This is the signal to act on if you want to tell the customer their wallet is ready.

**Observable result:** the wallet has a balance, and the agent can now spend from it.

</Step>

<Step title="Connect the customer to their AI agent">

The agent sees wallets only once Mitu knows which customer is connected.

<Tabs>

<Tab title="Customer key">

Give the customer the MCP URL and the `mcpk_...` key from the create response. Their client sends it on every request:

```http
x-api-key: mcpk_3a6f9d2a...
```

`Authorization: Bearer <key>` is also accepted. The key was returned once, so if it is lost, issue a new customer key rather than trying to recover it.

</Tab>

<Tab title="OAuth">

Enable customer sign-in on your integration and configure your identity provider. The customer adds the MCP URL and nothing else; the client discovers the flow and prompts them to sign in with the account they already have with you.

The person who signs in must resolve to the customer that owns the wallet. Mitu maps them from the identity provider's `sub`, which is what `client_reference_id` was set to when the customer was created.

</Tab>

</Tabs>

{/* SCREENSHOT: docs/assets/integration-guides/issue-wallets/connect-agent.png
     Caption: "Connect the customer's AI client so Mitu can identify which
     wallets belong to them." Never show a real customer key. */}

[MCP authentication](/platform/mcp/authentication) covers both in depth.

</Step>

<Step title="Confirm the agent has wallet tools">

Four tools appear for that customer:

```text
list_wallets()                      the names they hold
get_balance({ wallet? })            a balance, or all of them
get_address({ wallet? })            where to fund one, labelled by chain
pay({ endpoint, method?, body?, wallet? })
```

`get_balance` with several wallets and no name answers for all of them, because reading harms nothing. `get_address` and `pay` require a name when there is more than one.

[Wallet tools](/platform/agent-wallets/wallet-tools) has the exact arguments and refusal behaviour.

**Observable result:** the customer's client lists these alongside your own endpoint tools.

</Step>

<Step title="Let the agent use the wallet">

```text
pay({ endpoint: "/orders", method: "POST", body: {...}, wallet: "Travel" })
```

`endpoint` is a path on your own service, as named in the 402. It is not a URL, and the agent cannot point it elsewhere. A tool that paid an arbitrary address supplied by a model would be one a prompt injection could aim anywhere.

Mitu checks, in order:

```text
Is this wallet the customer's?
Is the customer frozen?
Is the destination blocked?
Does the balance cover it?
Does it stay inside the monthly limit?

Within: settle now
Over:   hold, and raise an approval request
```

None of that is offered to the caller. It is applied to the payment.

</Step>

<Step title="Handle approval">

A payment that would exceed the monthly limit does not fail. It is held, an approval request is raised for the customer, and `pay` answers `pending_approval` with the amount.

<Warning title="pending_approval is neither a settlement nor a decline">
The money has not moved and it still might. An agent that reports it as a failure tells the customer their booking did not happen when it is waiting on them. One that reports it as success tells them it did when it has not.
</Warning>

Design your product for a workflow that pauses on a person: hold the task, tell the customer what needs approving, and resume when it clears.

</Step>

<Step title="Track spending">

`wallet.debited` records money leaving.

```json title="wallet.debited"
{
  "event": "wallet.debited",
  "event_data": {
    "customer_id": "cus_0t9549fps3xd",
    "customer_ref": "auth0|68f3c2a1b9",
    "amount": "0.035000",
    "currency": "USDC",
    "network": "base",
    "reason": "payment",
    "destination": {
      "type": "merchant",
      "name": "AgentPizza",
      "address": "0x1DDb114B971E67241B3aF19C958a01EBBfb1B6DD"
    },
    "transaction_id": "f5533e85-16d8-4f58-ba22-86dba59c6a15",
    "tx_hash": "0xfe093b9a...",
    "delivered": true
  }
}
```

`reason` is `payment`, `withdrawal` or `reversal`. `delivered` says whether the customer got what they paid for.

If you both issued the wallet and received the payment, you also get `payment.completed` for your side. They describe one movement and join on **`tx_hash`**, not `transaction_id`, which differs because each names a record in a different system.

</Step>

<Step title="Retrieve a customer's wallets">

```bash title="Request"
curl --request GET \
  --url https://api.mitu.ai/v1/customers/cus_ds9hazr8jd3l/wallets \
  --header "x-api-key: $MITU_API_KEY"
```

```json title="200 OK"
[
  {
    "id": "wal_fc2ff966abc04de09c22",
    "customer_id": "cus_ds9hazr8jd3l",
    "name": "Travel",
    "currency": "USDC",
    "limits": { "per_payment": 250, "monthly": 2000,
                "approve_above": 150, "currency": "USD" },
    "created_at": "2026-09-11T15:01:32.760Z"
  }
]
```

Names and limits come back together. Addresses do not: only the create response carries those.

This is how you show a customer their pots in your own product, and how you check what exists before issuing another.

</Step>

</Steps>

## Complete example: a Travel wallet

<Steps>

<Step title="You already have the customer">
`your_user_8841` in your own system. You create the Mitu customer with that as `client_reference_id`, and get back `cus_ds9hazr8jd3l` and an `mcpk_...` key.
</Step>

<Step title="You issue Travel">
```bash
curl --request POST \
  --url https://api.mitu.ai/v1/customers/cus_ds9hazr8jd3l/wallets \
  --header "x-api-key: $MITU_API_KEY" \
  --data '{ "name": "Travel", "limits": { "monthly": 3000 } }'
```
</Step>

<Step title="The customer funds it">
They send USDC to the Base address from the create response.
</Step>

<Step title="The deposit lands">
`wallet.credited` fires with the amount, the network and `balance_after`.
</Step>

<Step title="They connect their client">
With the `mcpk_...` key, or by signing in through your OAuth. Mitu now knows which customer is asking.
</Step>

<Step title="Their agent sees Travel">
```text
list_wallets()                    -> Travel
get_balance({ wallet: "Travel" }) -> the balance in that pot
```
</Step>

<Step title="It reaches a payment">
One of your endpoints answers 402, and the agent settles it from the wallet the customer named.
</Step>

<Step title="Mitu checks the controls">
The wallet is theirs, the balance covers it, and it stays inside the monthly limit. It settles.
</Step>

<Step title="You see the movement">
`wallet.debited` arrives with the amount, the destination and `delivered: true`.
</Step>

</Steps>

## Errors and edge cases

<AccordionGroup>

<Accordion title="The customer already exists">
Reuse them. `client_reference_id` is what makes the create call resolve to the same customer rather than making a second, so sending the same reference is safe.
</Accordion>

<Accordion title="The wallet name already exists">
The create returns the wallet that already exists, and raises no `wallet.created`. Retrying is safe and does not produce a duplicate pot.
</Accordion>

<Accordion title="The customer has no wallet">
A valid state, and the default one. Their wallet list is empty and they have no balance or address. Show them as a customer without a wallet, not as an error.
</Accordion>

<Accordion title="The wallet has no funds">
Also valid. A wallet is created empty. A payment attempted against it is refused for insufficient funds rather than held, so the customer is told to top up rather than left waiting on an approval that will never arrive.
</Accordion>

<Accordion title="The monthly limit would be exceeded">
Held, not refused. An approval request is raised and `pay` answers `pending_approval`.
</Accordion>

<Accordion title="Several wallets and none named">
Refused, with the available names returned. Put the choice to the customer rather than picking.
</Accordion>

<Accordion title="An unknown wallet name">
Refused, with no fallback to the nearest match or to a default. A typo and an invented name behave the same way.
</Accordion>

<Accordion title="Funds sent to the wrong network">
Not recoverable. Base and Tempo share the EVM address; Solana's is different. The only defence is showing the network beside the address before the transfer.
</Accordion>

<Accordion title="Paid, but not delivered">
Settlement happens before your endpoint is called, so a refusal afterwards leaves the customer charged with nothing to show. `pay` answers `settled_not_delivered` and `wallet.debited` carries `delivered: false`. Never retry: that charges them twice. See [paid but not delivered](/platform/payments/agent-payments).
</Accordion>

</AccordionGroup>

## Security

**Your merchant key** creates customers, wallets and payment links, and never leaves your server.

**The customer key** identifies one customer to your MCP. It holds no funds, cannot create a wallet, cannot read your account, and never reaches your own API.

**The agent** holds no key and no wallet credential. It cannot create a wallet, move money between wallets, withdraw, change a limit, or spend from a wallet it was not given.

**Limits** are enforced by Mitu on the payment, not offered to the caller. An agent that has been talked into wanting to spend still meets the same balance and the same ceiling.
