---
title: Connect your product to AI agents
subtitle: Make your existing products, services and APIs available to AI agents through MCP, keeping your backend, your customer accounts and your business logic.
---

Your application is one way customers use your product. An AI agent becomes another. Mitu sits in front of the API you already run and turns the operations you choose into tools that compatible AI clients can discover and call.

```text
Your existing API
        |
Connect it to Mitu
        |
Choose the operations agents can use
        |
Describe each one as a tool, with schemas
        |
Mitu serves them over MCP
        |
A customer connects from an AI client
        |
The agent calls a tool
        |
Mitu calls your API
        |
Your API answers exactly as it always has
```

This is about adding a channel, not building an agent. Nothing here requires payments or wallets: an entirely free integration is a valid one.

<Note title="Connecting the base URL does not expose your API">
Only the operations you register become tools. The rest of what lives behind that base URL stays where it is.
</Note>

## What you will build

1. Your API connected, reachable, and signing verified.
2. The operations you want agents to use, registered as tools.
3. Request and response schemas an agent can act on.
4. A decision on which operations need a signed-in customer.
5. A customer connected from an AI client.
6. The agent discovering and calling a tool.
7. Your backend receiving the call and answering normally.

## Before you begin

You need a Mitu merchant account, an HTTPS API that Mitu can reach, and at least one operation worth exposing.

<Steps toc={true}>

<Step title="Connect your API">

In the dashboard, set the base URL Mitu forwards to, and the health-check path if you have one.

```text
API base URL        https://api.example.com
Health check path   /healthz
```

**Mitu holds no credential for your API.** Authenticity runs the other way: Mitu signs every forwarded request with a secret it issues you, shown on the Integration page as `mps_...`, and your backend verifies it.

```text
sk_live_... / sk_test_...   your merchant key, for Mitu's own API
mps_...                     signs requests Mitu makes TO your API
whsec_...                   signs webhook deliveries Mitu sends you
mcpk_...                    one customer's key for reaching your MCP
```

Requests are forwarded with a **30 second** timeout.

**Check before moving on:** the base URL is saved, the health check passes, and your backend holds the signing secret.

</Step>

<Step title="Add the operations agents can use">

Register the operations that are meaningful to an agent, not everything you serve. A tool list containing things an agent should never call makes it more likely that it calls one.

A booking product might expose four of its operations:

```text
GET  /locations        list_locations
GET  /availability     check_availability
POST /bookings         create_booking
GET  /bookings/{id}    get_booking
```

Each record carries the routing, the text the model reads, and the schemas:

```yaml
name: create_booking
method: POST
path: /bookings
description: Creates a booking at a location for a given date, time and party size
when_to_use: Use after the customer has confirmed the location, date, time and party size
input_schema: { }
output_schema: { }
requires_auth: true
pricing_type: free
rate_limit_per_minute: 60
is_public: true
```

`is_public: false` keeps an endpoint out of the tool list while leaving it callable, which is how you stage something before announcing it.

{/* SCREENSHOT: docs/assets/integration-guides/connect/add-operation.png
     Caption: "Register an operation and describe when an agent should use
     it." Show name, method, path, description and pricing. */}

[MCP endpoints](/platform/mcp/endpoints) has every field.

</Step>

<Step title="Write the description and when_to_use">

A model sees `name`, `description`, `when_to_use` and the schemas. Nothing else. These four fields are the entire basis on which it decides.

```text
Poor      create_booking
          Creates booking

Better    create_booking
          Creates a booking at a location for a given date, time and party size
          Use after the customer has confirmed the location, date, time and party size
```

Name tools for the action, in the `verb_noun` form models are used to. Describe what the operation does to what, and for whom. Then say in `when_to_use` what must already be true before the call makes sense, which is what stops a model reaching for the wrong tool when two look similar.

</Step>

<Step title="Define the request schema">

The input schema becomes the tool's arguments. The more precise it is, the fewer malformed calls reach your API.

```json title="input_schema"
{
  "type": "object",
  "properties": {
    "location_id": {
      "type": "string",
      "description": "Location identifier from list_locations"
    },
    "date": {
      "type": "string",
      "format": "date",
      "description": "Booking date, YYYY-MM-DD"
    },
    "time": {
      "type": "string",
      "description": "24-hour local time, HH:MM"
    },
    "party_size": {
      "type": "integer",
      "minimum": 1,
      "maximum": 12,
      "description": "Number of people"
    },
    "seating": {
      "type": "string",
      "enum": ["indoor", "outdoor", "bar"]
    }
  },
  "required": ["location_id", "date", "time", "party_size"]
}
```

Four things earn their keep here:

- **Field names the model can reason about.** `location_id` beats `lid`.
- **A description on every field**, especially where a value comes from another tool. "Identifier from `list_locations`" tells the model to call that first.
- **`required` that matches reality.** Marking an optional field required makes the model invent values for it.
- **Enums wherever the set is closed.** An enum removes a whole class of guessing.

Keep the schema aligned with what your API actually validates. A schema looser than your API produces calls your API rejects; one tighter than your API hides capability.

</Step>

<Step title="Define the response schema">

The output schema tells the agent what it is getting back, so it can use the result rather than guess at it.

```json title="output_schema"
{
  "type": "object",
  "properties": {
    "id": { "type": "string", "description": "Booking reference" },
    "status": { "type": "string", "enum": ["confirmed", "waitlisted"] },
    "location_id": { "type": "string" },
    "date": { "type": "string", "format": "date" },
    "time": { "type": "string" },
    "party_size": { "type": "integer" }
  },
  "required": ["id", "status"]
}
```

This matters more than it looks. An agent that knows `id` is the booking reference can quote it back to the customer and pass it to `get_booking` later. One that does not has to infer which field mattered from a wall of JSON, and will sometimes pick wrong.

</Step>

<Step title="Or import an OpenAPI document">

If you already maintain one, import it instead of adding operations by hand. Mitu parses the document and creates one endpoint per operation with the schemas attached, which you can then edit.

The descriptions and `when_to_use` are still worth a pass afterwards. An OpenAPI `summary` is written for a developer reading a reference; `when_to_use` is written for a model choosing between tools, and they are rarely the same sentence.

{/* SCREENSHOT: docs/assets/integration-guides/connect/openapi-import.png
     Caption: "Import an OpenAPI document to create endpoints in bulk." */}

</Step>

<Step title="Decide which operations need a signed-in customer">

`requires_auth` is per endpoint, so a public catalogue can stay open while anything touching an account does not.

| Usually needs a customer | Usually does not |
| --- | --- |
| Saved addresses and preferences | A public catalogue or menu |
| Account-specific pricing | Published availability |
| Order or booking history | Location lists |
| Creating something against a profile | General stock levels |

Two methods identify the customer. A **customer key** is one you provision and hand over, sent as `x-api-key: mcpk_...`. **OAuth** lets the customer sign in with the account they already have with you, and no key is handed out at all.

<Warning title="OAuth sign-in does not create a wallet">
It creates a Mitu customer, mapped from your identity provider's `sub`. Wallets are a separate product and a separate decision.
</Warning>

[MCP authentication](/platform/mcp/authentication) covers both without repeating the setup.

</Step>

<Step title="Connect an AI client">

```text
URL         https://mcp.yourdomain.com/mcp, or https://mcp.mitu.ai/mcp
Transport   Streamable HTTP
```

With a customer key, the customer supplies the URL and their `mcpk_...`. With OAuth, they supply only the URL: an unauthenticated `initialize` answers 401 with a `WWW-Authenticate` header naming the resource metadata, which is what makes the client offer a sign-in rather than fail.

{/* SCREENSHOT: docs/assets/integration-guides/connect/add-connection.png
     Caption: "Adding the MCP as a connection in an AI client." Never show a
     real customer key. */}

[Domain and integration](/platform/mcp/domains) covers moving to your own URL.

</Step>

<Step title="Confirm the agent can discover your tools">

Once connected, the client lists the tools registered for your service. That list is the confirmation the channel works.

```text
list_locations       GET   /locations       free
check_availability   GET   /availability    free
create_booking       POST  /bookings        free
get_booking          GET   /bookings/{id}   free
call_endpoint        any path on your service
```

`call_endpoint` is always present alongside the named tools. It is a fallback for paths without a tool of their own, such as a sub-path under a registered one. The named tools are what an agent should reach for, because they carry your description and your schemas.

If nothing appears, check that the endpoints are registered and `is_public`, and that the customer's credential is being sent.

</Step>

<Step title="Call a tool, and see what reaches your backend">

The customer asks for a table. The agent picks `create_booking` and calls it. What arrives at your API is your own contract:

```http
POST https://api.example.com/bookings
content-type: application/json
user-agent: <the caller's>
x-mitu-agent-id: anonymous
x-mitu-request-id: req_5f13b916
x-mitu-amount-charged: 0
x-mitu-signature: t=1757601046,v1=9f3c4a...b2d4
```

```json
{
  "location_id": "lagos-01",
  "date": "2026-09-20",
  "time": "19:30",
  "party_size": 4
}
```

The body is the body your API already understands. You do not add `agent_instruction`, `llm_context` or a conversation transcript unless your own API genuinely wants them. Mitu converts the tool call into your existing contract.

**On the headers, three things are worth knowing.**

Only `content-type`, `accept` and `user-agent` are forwarded from the caller. Everything else is dropped, and the Mitu headers are set afterwards, so a caller cannot smuggle in an `x-mitu-*` value of its choosing.

The incoming `Authorization` is always stripped, because it is the payment credential and is Mitu's business rather than yours. When you use OAuth, the customer's own token arrives separately and is re-emitted to you as `Authorization`, so your existing endpoint keeps working unchanged.

<Warning title="On a free call the amount header is present and reads `0`">
It is absent only on a dynamic-pricing quote. So `x-mitu-amount-charged` being present does not mean you were paid, and branching on presence alone will treat every free call as a paid one. Compare the value, or branch on your endpoint's pricing model.
</Warning>

Free endpoints are rate limited per endpoint, at `rate_limit_per_minute`, defaulting to 60. Over it, the agent receives a rate-limit response and your API is never called.

</Step>

<Step title="Verify the signature">

Free calls are signed too. Verify before you act, because everything else in the request is a plain header.

```text
x-mitu-signature: t=1757601046,v1=9f3c4a...b2d4

v1 = HMAC-SHA256(signing_secret, "{t}.{request_id}.{amount}.{raw_body}")
```

Use the raw bytes, use a timing-safe compare, and enforce the timestamp. [Request signature verification](/platform/security/request-verification) has the algorithm and a worked implementation.

For anything with side effects, deduplicate on `x-mitu-request-id`. A booking endpoint called twice for one request id is a double booking.

</Step>

<Step title="Return your normal response">

```json title="201 Created"
{
  "id": "bk_77213",
  "status": "confirmed",
  "location_id": "lagos-01",
  "date": "2026-09-20",
  "time": "19:30",
  "party_size": 4
}
```

Mitu passes it back to the agent through the call it started, adding `x-mitu-request-id` to the response. Hop-by-hop headers are stripped and `content-length` is recomputed; everything else you set comes through.

Your backend never needs to know the caller was an agent, beyond the headers it verified.

</Step>

<Step title="Handle errors in a way an agent can act on">

An agent reads your error and decides what to do next. A status with an empty body gives it nothing, so it guesses, and usually retries.

```json title="422 Unprocessable Entity"
{
  "error": "no_availability",
  "message": "No table for 4 at 19:30 on 2026-09-20. The nearest times are 18:45 and 20:30.",
  "alternatives": ["18:45", "20:30"]
}
```

That response lets the agent offer the customer something. `422` with no body makes it try again with the same values.

Say what was wrong, say whether retrying could work, and where a near miss exists, name it. Keep using your own status codes and shapes; this is about the body being informative, not about adopting a new error format.

</Step>

<Step title="Test the whole flow">

```text
1. Health check passes
2. The tools appear in a connected client
3. A free read returns real data
4. A write creates the thing, once
5. The same request id twice creates one record
6. A tampered body fails verification
7. An error returns a body the agent can use
```

Then add operations one at a time. A channel with four well-described tools is more useful than one with forty the model cannot choose between.

</Step>

</Steps>

## Adding paid operations later

Nothing in this guide requires payment, and a free channel is a complete integration. When you want an operation to charge, set its `pricing_type` and the payment layer appears in front of it without your endpoint changing.

[Accept payments from agents](/guides/integration-guides/accept-payment-from-agents) picks up exactly there.

## A worked example

<Steps>

<Step title="The existing product">
A restaurant booking service with four operations already serving its web and mobile apps.

```text
GET  /locations
GET  /availability
POST /bookings
GET  /bookings/{id}
```
</Step>

<Step title="You connect the API">
Base URL `https://api.example.com`, health check `/healthz`. The signing secret goes into your backend's config.
</Step>

<Step title="You register the four operations">
Each with a description, a `when_to_use`, and input and output schemas. `create_booking` and `get_booking` are marked `requires_auth: true`; the two reads are not.
</Step>

<Step title="A customer connects">
They add the MCP URL to their AI client and sign in with the account they already have with you.
</Step>

<Step title="They ask for a table">
"Book me a table for four at the Lagos branch on Saturday at 7:30."
</Step>

<Step title="The agent works it out">
`list_locations` to resolve "Lagos branch", `check_availability` for Saturday, then `create_booking`.
</Step>

<Step title="Your API answers">
```json
{ "id": "bk_77213", "status": "confirmed", "time": "19:30", "party_size": 4 }
```
</Step>

<Step title="The customer gets an answer">
"Booked, reference bk_77213, Saturday at 7:30 for four." The same booking, in the same database, made through the same endpoint as the app.
</Step>

</Steps>
